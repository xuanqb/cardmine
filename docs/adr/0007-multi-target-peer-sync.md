# 多目标对等 Anki 同步（前端共享）

- 状态：已接受
- 日期：2026-11-25

## 背景

用户原本把前端和后端卡片放在同一个 AnkiWeb 账号复习。现在朋友需要持续复习前端：前端由一份私有 RSS 面经源采集，cardmine 继续抓取、切题、整理为 `ready`，再把前端卡片同步到朋友的 AnkiWeb 账号。朋友账号当前为空。

用户明确要求：

- 两个账号不分主次，都双向同步。
- 朋友可以修改、删除、新增卡片，修改自动应用。
- 冲突进入队列，人工整卡选择。
- 朋友新增卡片按牌组自动归类。
- 牌组移动同步到模块；移出前端组视为取消共享。
- 删除双向传播；编辑与删除冲突时进入冲突队列。
- 前端 RSS 地址私密，不写入仓库。

旧实现是单 AnkiConnect、单 collection：`anki_sync` 一卡一行，`knowledge_point.anki_note_id` 是唯一映射，推送和拉取都只面向一个账号。ADR 0001 还规定“正面只由系统维护、Anki 正面修改一律进冲突”，与本需求的对等编辑冲突。

## 决策

### 1. 同步目标与组映射

- 引入「同步目标」：一个 Anki 集合，通过独立的 AnkiConnect 地址访问，拥有自己的笔记映射、同步状态和冲突。
- `anki_target` 保存名称、AnkiConnect URL、启用状态和运行状态；AnkiWeb 凭据属于目标容器，不进入 cardmine。
- `group_target` 保存顶层组到目标的多对多映射。一个组可映射多个目标，一个目标可覆盖多个组；未映射的组不同步。
- 卡片按所属顶层组的映射分发；组由模块的顶层祖先决定，不按卡片内容改判。
- 同一组的所有映射目标对等双向；cardmine 是内容汇聚的中枢，不设主账号。

### 2. 连接与初始化

- 第二个账号使用独立的 AnkiConnect 容器、独立数据卷和独立 AnkiWeb 凭据；cardmine 只保存目标 URL。
- note 类型保持全局配置（`anki_model`）。目标为空时，首次同步通过 AnkiConnect 创建同名字段的 note 类型，朋友不需要手动导入模板。
- 升级时把现有顶层组预映射到当前账号；前端组随后由用户在页面映射到朋友账号。
- 目标首次接入时回填该组现有的 `ready` 卡片，之后持续同步新卡。

### 3. 同步范围

- 只推送 `ready` 卡片；`draft` 不推送；`archived` 从所有目标删除。
- 拉取只处理目标映射组子树内的牌组和配置的 note 类型；目标里的其他牌组、其他 note 类型忽略。
- 复习进度、标签、旗帜、note 类型不同步；标签和旗帜仍只由系统维护。
- 朋友新增的卡片直接成为 `ready`，登记目标 note 映射，并分发到其他目标。

### 4. 合并与冲突

- 每个目标独立维护笔记映射和字段基线；同步基线仍表示“最近一次成功同步后双方一致的内容”。
- 单侧相对基线发生变化时自动应用，并分发到其他目标。
- 系统与某个目标都相对基线发生变化且内容不同，或两个目标都发生变化且内容不同，记为整卡冲突。
- 正面不再只由系统维护：目标侧的正面修改自动应用；若新正面与同组其他卡片重复，记为整卡冲突。这一点取代 ADR 0001 的正面规则。
- 冲突队列展示 cardmine 与各目标版本；人工选择保留哪一方的整张卡片；选择后分发到所有目标。
- 一边编辑、一边删除同一张卡，不自动删除，进入冲突队列。

### 5. 目标侧新增与归类

- 只处理组子树内的牌组；子树内新牌组自动创建对应模块。
- 子树外的新顶层牌组忽略，不创建新组。
- 新卡按同组正面精确去重：
  - 同正面、同背面：绑定已有卡，不重复创建。
  - 同正面、不同背面：整卡冲突。
- 字段缺失、note 类型不符或无法解析的卡片跳过，并在同步报告中列出。

### 6. 牌组移动与移除

- 组内移动：更新卡片模块，并同步到其他目标。
- 移出组子树：视为「移除」。卡片仍留在 cardmine 与其他目标，目标侧笔记停止同步，不删除；移回组子树后自动恢复。
- 根牌组改名或移出同样视为移除，不跟随修改顶层结构。
- 区分方式：
  - note ID 已不存在 → 删除。
  - note 仍存在、但卡片当前牌组在组子树之外 → 移除。
  - note 仍存在、牌组在组子树内 → 组内移动。

### 7. 删除传播

- 任一目标确认 note 不存在，且该卡片自上次同步后未被编辑：归档卡片，并从其余目标删除同一笔记。
- 若同时存在编辑：进入冲突队列，不删除。
- 目标不可达或同步失败不触发删除；必须在一次成功拉取中确认缺失后才传播。
- 归档仍遵循 ADR 0003：系统保留卡片作为去重锚点，Anki 侧删除。
- 对等删除会丢失其他账号的复习记录，这是双向同步的代价。

### 8. 触发、失败与媒体

- 保留手动推送/拉取和抓取结束后的自动推送；不新增定时同步。
- 每个目标独立启用、独立状态、独立错误；一个目标失败不阻塞其他目标。
- 媒体仍使用中央媒体库；推送前比较目标侧同名媒体，内容不同则记为冲突，不静默覆盖。

### 9. 数据迁移

- 现有 `anki_sync` 行迁移为当前账号对应的目标；主键从 `kp_id` 改为 `(kp_id, target_id)`。
- `knowledge_point.anki_note_id` 不再作为权威映射，所有读写改为按目标的笔记映射；迁移完成后删除该列。
- 现有字段级 `anki_conflict` 收敛为整卡冲突；未解决冲突保留快照可读。
- 现有 `anki_url` 设置迁移为第一个同步目标。

## 后果

- 迁移 014 新增 `anki_target`、`group_target`，重建 `anki_sync` 与冲突表，并为现有数据回填目标。
- `anki/service.py` 从单 client 改为按目标 fan-out；推送、拉取、归档删除、旗帜、接管和统计都要按目标读取映射。
- 页面新增同步目标管理、组目标映射、每目标状态和整卡冲突页；冲突 UI 从字段级改为整卡。
- 部署新增第二个 AnkiConnect 容器和凭据；首次同步自动创建 note 类型并回填前端卡片。
- 风险：
  - 对等删除会跨账号传播，误删不可逆。
  - 正面修改会改变组内去重键，可能产生冲突。
  - 两个账号同时编辑会产生冲突，需要人工处理。
  - AnkiWeb 并发同步可能要求 full sync；目标容器必须配置为失败而不是强制覆盖。
  - 过滤牌组/临时牌组可能干扰“移除”判断，无法确认时报告而不删除。
- 测试需要两个独立 collection 或 fake AnkiConnect；重点覆盖三向合并、正面冲突、编辑对删除、移除/恢复、目标侧新增去重和媒体冲突。

## 备选方案

- 只导出 apkg：简单，但不能持续给朋友新题。
- 单向镜像：朋友不能参与维护，与“对等双向”不符。
- 主从账号：需要定义主账号，与“不分主次”不符。
- 给朋友单独部署一套 cardmine：重复采集、切题和维护。
- 在代码里写死前端目标：不可配置，且私密地址不应进入仓库。

## 取代关系

- 取代 ADR 0001 中“正面只由系统维护、冲突按字段处理”的规则；背面双向、同步基线、媒体回写和冲突保护仍适用。
- 扩展 ADR 0003 的归档删除到所有映射目标。
